# План проверок участников

Общая основа: [паспорт, §4–5](../project.md), SSDF 1.1 и выбранные требования ASVS 5.0.0. Проверяем локальный TaskFlow на синтетических данных. Задания описывают предстоящую работу, а не выполненный вклад.

| Исполнитель | Основная работа | Взаимная проверка | Результат |
| --- | --- | --- | --- |
| Роман Бекетов, `rbeketov` | М1: права и изоляция; М3: зависимости и конфигурация | Повторить один CSRF-сценарий и один сценарий экранирования Ярослава | PR с отчётом М1/М3 и review PR Ярослава |
| Ярослав Кузьмин, `yarikTri` | М2: ввод/вывод и CSRF; независимая установка архива | Повторить запретный сценарий М1 и проверить вывод аудита М3 Романа | PR с отчётом М2/запуска и review PR Романа |

Порядок: сначала каждый готовит свой отчёт и PR; затем обмениваемся проверкой и созваниваемся. Чтобы не ждать друг друга, отчёты оформляем без автоматического закрытия Issues. Закрываем задачи после взаимного review и обсуждения.

В каждом результате указываем не только метод М1–М3, но и **практику SSDF / требование ASVS**, которое проверяем. Это связь «основание — действие — результат», а не заявление о полном соответствии стандартам. Сокращения PW.7, PW.8 и RV.2 на слайдах означают соответственно PW.7.1–7.2, PW.8.1–8.2 и RV.2.1–2.2 SSDF 1.1.

## Роман: доступ, зависимости и проверка результата Ярослава

GitHub Issue: [#1](https://github.com/rbeketov/rbpo-yavkaib/issues/1), исполнитель `rbeketov`.

Оценка: 3–4 часа на основные проверки и около часа на review.

1. **PO.1.2, PO.2.1 — требования и ответственность.** Прочитать §1–5 паспорта и обоснование варианта A. Записать в задаче свою область и второго проверяющего. Объяснить своими словами: SSDF задаёт процесс, ASVS уточняет свойства веб-приложения.
2. **PW.8.1–8.2 — план и выполнение тестов.** Создать ветку `roman/security-checks`. Записать `git rev-parse HEAD`, версии Python и пакетов. Установить и запустить проект по README. Сохранить вывод `python scripts/verify.py --output /tmp/roman-verification.json`.
3. **М1: PO.1.2, PW.7.1–7.2, PW.8.1–8.2; ASVS 8.1.1, 8.2.1–8.2.3, 8.3.1.** Составить свою таблицу ожидаемых прав, затем сопоставить с `tracker/permissions.py`, `views.py`, `forms.py`. Проверить owner/editor/viewer и постороннего: чтение, создание/изменение, комментарий, удаление, управление участниками. Негативный результат подтверждать ответом сервера **и отсутствием изменения данных**. Получить матрицу прав, результаты и замечания к коду.
4. **М1: PW.8.1–8.2; ASVS 8.2.2–8.2.3, 8.3.2.** Отдельно проверить чужой project/task/membership ID, подмену owner/author, отзыв членства и понижение editor до viewer без нового входа. Существующие тесты использовать как опору, а ожидаемый результат выводить из требования. Для реально отсутствующего существенного случая добавить тест.
5. **М3: RV.2.1–2.2 — оценка риска и решение по находке.** Запустить аудит точного `requirements.txt` через `pip-audit` в отдельной среде средства. Сохранить версию средства, дату запроса, команду и отчёт. При сетевой ошибке отметить сбой, а не «уязвимостей нет». Каждую находку разобрать по первичному advisory: применимость к версии/функции, влияние, исправление, решение. Если находок нет, указать границы этого вывода. Сканер даёт входные данные для RV.2; практика не предписывает именно `pip-audit`.
6. **М3: PS.1.1 — защита кода и конфигурации; PS.3.1 — состав сохраняемого выпуска.** Сверить доступ к репозиторию, `.env.example`, `settings.py`, `.gitignore`, права workflow и состав архива. Рабочие `.env`, SQLite, cookie и секреты не публиковать. Проверка остальных настроек приложения — дополнительная проверка М3. `pip check` подтверждает совместимость, а не отсутствие CVE. `check --deploy` не подтверждает безопасность production.
7. **PW.7.2, PW.8.2, RV.2.1–2.2 — запись результатов и решений.** Сохранить `evidence/review/roman/report.md`, очищенные машинные отчёты и открыть PR с ссылкой на Issue. В таблице каждого случая: ID, **практика SSDF и пункт ASVS**, требование/риск, commit, роль/условия, действие, ожидание, факт, ссылка на свидетельство, вывод. Для найденного дефекта указать действие и после исправления повторить тест по PW.8.
8. **PO.2.1, PW.7.1–7.2, PW.8.1–8.2; ASVS 1.2.1, 3.5.1.** После PR Ярослава прочитать связанный код, самостоятельно повторить отказ без CSRF-токена и успешный запрос с токеном; проверить экранирование опасного текста. Оставить review с проверенной версией, командами, результатом и замечаниями.

**Готово:** собственный отчёт воспроизводим, выводы основаны на фактах, Ярослав проверил существенный сценарий, review его PR сохранён. Исправления оформляются отдельно с повторной проверкой. Изобретать уязвимость ради отчёта не нужно.

## Первоисточники для обоих планов

Практики процесса: [NIST SSDF 1.1, SP 800-218](https://csrc.nist.gov/pubs/sp/800/218/final). Действия пары и условия принятия — наша адаптация семи групп из §2 паспорта.

| Требования ASVS 5.0.0 | Что проверяем в TaskFlow | Основной исполнитель |
| --- | --- | --- |
| [8.1.1, 8.2.1–8.2.3, 8.3.1–8.3.2](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x17-V8-Authorization.md) | Документированные права, доступ к действиям/объектам/полям, серверная проверка и применение изменения роли | Роман; Ярослав независимо проверяет |
| [1.2.1](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x10-V1-Encoding-and-Sanitization.md) | Экранирование пользовательского текста в контексте HTML | Ярослав; Роман повторяет |
| [2.1.1, 2.2.1–2.2.2](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x11-V2-Validation-and-Business-Logic.md) | Правила допустимого ввода и их проверка на сервере | Ярослав |
| [3.5.1, 3.5.3, 3.7.2](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x12-V3-Web-Frontend-Security.md) | CSRF, безопасные HTTP-методы, ограничение внешних перенаправлений | Ярослав; Роман повторяет CSRF |
| [7.4.1](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x16-V7-Session-Management.md) | Завершённая сессия больше не даёт доступ | Ярослав |

Это выбранные требования в границах локального приложения, а не полная проверка глав ASVS или подтверждение уровня. Для конкретного случая участник указывает один или несколько действительно относящихся к нему пунктов, ожидаемое поведение и наблюдаемый результат.

## Совместный созвон после личных проверок

На 25–30 минут: каждый показывает свой отчёт и объясняет один запретный сценарий. Сверяем выводы и замечания, выбираем полезное улучшение по фактам, определяем его автора и проверяющего. Репетируем 4 минуты защиты по [слайдам](../presentation/taskflow-ek1.pptx). Итоги записываем в Issues; решения о продуктовом выпуске принимаем только по GATE-R. Для ЭК1 достаточно концепции и плана, завершённая апробация М1–М3 относится к следующим этапам курса.
