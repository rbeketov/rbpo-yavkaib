# План проверок участников

Общая основа: [паспорт, §4–5](../project.md), SSDF 1.1 и выбранные требования ASVS 5.0.0. Проверяем локальный TaskFlow на синтетических данных. Задания описывают предстоящую работу, а не выполненный вклад.

| Исполнитель | Основная работа | Взаимная проверка | Результат |
| --- | --- | --- | --- |
| Роман Бекетов, `rbeketov` | М1: права и изоляция; М3: зависимости и конфигурация | Повторить один CSRF-сценарий и один сценарий экранирования Ярослава | PR с отчётом М1/М3 и review PR Ярослава |
| Ярослав Кузьмин, `yarikTri` | М2: ввод/вывод и CSRF; независимая установка архива | Повторить запретный сценарий М1 и проверить вывод аудита М3 Романа | PR с отчётом М2/запуска и review PR Романа |

Порядок: сначала каждый готовит свой отчёт и PR; затем обмениваемся проверкой и созваниваемся. Чтобы не ждать друг друга, отчёты оформляем без автоматического закрытия Issues. Закрываем задачи после взаимного review и обсуждения.

## Роман: доступ, зависимости и проверка результата Ярослава

GitHub Issue: [#1](https://github.com/rbeketov/rbpo-yavkaib/issues/1), исполнитель `rbeketov`.

Оценка: 3–4 часа на основные проверки и около часа на review.

1. Прочитать §1–5 паспорта и обоснование варианта A. Объяснить своими словами: SSDF задаёт процесс, ASVS уточняет свойства веб-приложения.
2. Создать ветку `roman/security-checks`. Записать `git rev-parse HEAD`, версии Python и пакетов. Установить и запустить проект по README. Сохранить вывод `python scripts/verify.py --output /tmp/roman-verification.json`.
3. Для М1 составить свою таблицу ожидаемых прав по паспорту, затем сопоставить с `tracker/permissions.py`, `views.py`, `forms.py`. Проверить owner/editor/viewer и постороннего: чтение, создание/изменение, комментарий, удаление, управление участниками. Негативный результат подтверждать ответом сервера **и отсутствием изменения данных**.
4. Отдельно проверить чужой project/task/membership ID, подмену owner/author, отзыв членства и понижение editor до viewer без нового входа. Существующие тесты использовать как опору, а ожидаемый результат выводить из требования. Для реально отсутствующего существенного случая добавить тест.
5. Для М3 запустить аудит точного `requirements.txt` через `pip-audit` в отдельной среде средства. Сохранить версию средства, дату запроса, команду и отчёт. При сетевой ошибке отметить сбой, а не «уязвимостей нет». Каждую находку разобрать по первичному advisory: применимость к версии/функции, влияние, исправление, решение. Если находок нет, указать границы этого вывода.
6. Сверить `.env.example`, `settings.py`, `.gitignore`, workflow и состав архива. Рабочие `.env`, SQLite, cookie и секреты не публиковать. `pip check` подтверждает совместимость, а не отсутствие CVE. `check --deploy` не подтверждает безопасность production.
7. Сохранить `evidence/review/roman/report.md`, очищенные машинные отчёты и открыть PR с ссылкой на Issue. В таблице каждого случая: ID, требование/риск, commit, роль/условия, действие, ожидание, факт, ссылка на свидетельство, вывод.
8. После PR Ярослава самостоятельно повторить отказ без CSRF-токена и успешный запрос с токеном; проверить экранирование опасного текста. Оставить review с проверенной версией, командами, результатом и замечаниями.

**Готово:** собственный отчёт воспроизводим, выводы основаны на фактах, Ярослав проверил существенный сценарий, review его PR сохранён. Исправления оформляются отдельно с повторной проверкой. Изобретать уязвимость ради отчёта не нужно.

## Ярослав: ввод, CSRF, независимый запуск и проверка результата Романа

GitHub Issue: [#2](https://github.com/rbeketov/rbpo-yavkaib/issues/2). Исполнитель указан в описании; поле Assignee оставлено свободным.

Оценка: 3–4 часа на основные проверки и около часа на review.

1. Прочитать §1–5 паспорта и обоснование варианта A. Сверить, что границы и распределение ролей понятны, подготовить вопросы к созвону.
2. Скачать архив `ek1`, записать commit тега и SHA-256 ZIP. Распаковать в новый каталог, создать новую `.venv`, установить зависимости, выполнить миграции и seed по README. Запустить verifier и браузерную демонстрацию. Зафиксировать ОС, Python, пакеты, команды и фактический результат. Не использовать готовую среду Романа.
3. Создать ветку `yaroslav/input-checks`. Для М2 сопоставить выбранные требования ASVS 5.0.0 с формами и шаблонами. В отчёте привести точные пункты и ссылки на первоисточник; уровень соответствия не заявлять.
4. Проверить, что HTML/скрипт в названии, описании и комментарии отображается как текст и не исполняется. Проверить пустые поля, предельную и превышенную длину, недопустимый статус и подмену серверных полей. Проверять ответ и состояние данных; скриншота интерфейса недостаточно.
5. Проверить изменяющий POST без CSRF-токена через клиент с `enforce_csrf_checks=True` и такой же допустимый POST с корректным токеном. GET не должен удалять, комментировать или выполнять logout. Проверить вход/выход и отказ во внешнем redirect.
6. Сохранить `evidence/review/yaroslav/report.md`, очищенный лог запуска и отчёты. В таблице каждого случая: ID, требование/риск, commit, условия, действие, ожидание, факт, свидетельство, вывод. Открыть PR с ссылкой на Issue.
7. После PR Романа независимо выбрать запрет из матрицы прав и повторить его без копирования готового теста. Прочитать проверку роли и выборку объекта. Проверить один вывод CVE-триажа по первичному advisory либо ограничения отчёта без находок. Оставить review с версией, шагами и результатом.

**Готово:** чистый запуск воспроизведён, отчёт М2 проверяем, Роман повторил существенный случай, review его PR сохранён. Сбой установки или проверки оформляется как факт с шагами воспроизведения.

## Совместный созвон после личных проверок

На 25–30 минут: каждый показывает свой отчёт и объясняет один запретный сценарий. Сверяем выводы и замечания, выбираем полезное улучшение по фактам, определяем его автора и проверяющего. Репетируем 4 минуты защиты по [слайдам](../presentation/taskflow-ek1.pptx). Итоги записываем в Issues; решения о продуктовом выпуске принимаем только по GATE-R.
