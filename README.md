## Продукт: TaskFlow

Небольшой трекер задач на **Python / Django / SQLite**. Планируемый выпуск — **v1.0.0**.
За основу взят [вариант №2 курса](https://github.com/hse-rbpo-master-2026/course/blob/main/project-ideas/02-task-management-app.md).
Выбор трекера задач и трёх ролей подтверждён rbeketov. Детали реализации и распределение работы нужно согласовать с yarikTri.

Три роли назначаются **внутри проекта**, а не глобально. Пользователь может быть владельцем одного проекта и наблюдателем другого.

| Действие | Владелец | Редактор | Наблюдатель | Пользователь вне проекта |
| --- | --- | --- | --- | --- |
| Читать проект, задачи и комментарии | Да | Да | Да | Нет |
| Создавать/изменять задачи, писать комментарии | Да | Да | Нет | Нет |
| Удалять задачи | Да | Нет | Нет | Нет |
| Добавлять участников и менять их роли | Да | Нет | Нет | Нет |
| Удалять проект | Да | Нет | Нет | Нет |

**Минимальный объём:** вход и выход, проекты, участники, задачи с тремя статусами, текстовые комментарии.
Готовые серверные шаблоны Django; без отдельного frontend-приложения, вложений, уведомлений, платежей и внешних интеграций.
Учётные записи создаются локальной командой с синтетическими данными. Самостоятельная регистрация, почта и восстановление пароля не входят в первый выпуск.

Рамка для рассмотрения — NIST SSDF 1.1; выбранные требования OWASP ASVS 5.0.0 могут дополнить проверки аутентификации и доступа.
Это предварительный план, а не выполненная оценка соответствия.

## Как получить сильный результат

Оценка зависит от проверяемой связи «риск → метод → результат → улучшение → повторная проверка», а не от количества функций.

- Проверить таблицу прав доступа: попытки чтения и изменения чужих проектов, повышения собственной роли, записи от наблюдателя; проверять сервер, а не только видимость кнопок.
- Исследовать вход, выход, CSRF, вывод пользовательского текста и настройки Django.
- Проверить зависимости и воспроизводимость запуска; сохранять только существенные результаты.
- Выбрать полезное улучшение после анализа исходного состояния. Если уязвимости не найдены, улучшить покрытие тестами, конфигурацию, сборку или воспроизводимость — искусственно добавлять уязвимости не нужно.
- У каждого участника должен быть собственный содержательный участок работы и проверка части работы партнёра. Коммиты, PR и reviews должны отражать реальный вклад.

Предлагаемое разделение: yarikTri — сценарии задач и комментариев, обработка ввода и проверка соответствующих свойств; rbeketov — модель доступа, матрица негативных тестов и проверка конфигурации. Распределение предстоит согласовать; работы ещё не выполнены.
